# D10. API, traceability and limits (M4, M7)

Decision D10 of the OpenSolve Pipe decision record ([index](README.md)). Decisions override the specs; `docs/GOALS.md` overrides decisions. Code and tests cite this decision as `CLAUDE.md D10`.

---

- Every solved element carries a trace (inputs with their source, equations, correlations and data sources with citations, intermediates, notes stating the inequality that set its state); a methods-and-assumptions summary accompanies every solve. A value equal to a field's documented default is labeled "default". *(GOALS §4.2.)*
- A section with no path to a fixed head but with a running pump circulates: it is solved with an arbitrary reference head and reported with flows and head differences only, flagged `UNDETERMINED_PRESSURE`. PRV/PSV flows are coupled exactly in the Newton step (no lag).
- Solves run in a small worker pool (one solve per client at a time, bounded queue → 503 `SERVER_BUSY`) with a 45 s budget per request; abandoned requests are cancelled. The web app's Cancel, on a running solve and on a system curve being computed (PRD §4.2), aborts the request and says so; what was shown before stays, labelled current or out of date as before, and a late answer is dropped. Responses are gzip-compressed. *(Accessibility at near-zero hosting cost, GOALS §4.4.)*
- Privacy: request bodies are never logged; the access log drops query strings and client addresses; request-validation errors (`VALIDATION_ERROR`) never echo submitted values (SDD §5.1.2), while fluid-range, topology and not-found errors name the value or id at fault so it can be fixed (responses go only to the requester and are never logged). The interactive API docs (`/docs`, `/redoc`) load assets from third-party CDNs, so they are served only with `API_DOCS=1` (development); the schema is always at `/openapi.json`. The web app sends project data (fluid included) only in request bodies: `POST /api/v1/fluids/properties` takes a `FluidDefinition`; the `GET /fluids/{id}/properties?…` form stays for API users, though intermediaries may log its query. *(GOALS §4.5.)*
- System curves on demand (M7): the 41-point curves of every pump cost a solve per point and break the PRD §4.2 solve times, which a plain solve meets. The web app solves with `includeSystemCurve: false`; the pump chart fetches the curve of the pump being viewed from `POST /api/v1/system-curve`, for the exact project that was solved, one request at a time, cached with that solve and dropped by the next. It shows the loading state (with Cancel), failures, cancellations and points without a head; a curve is never shown with another solve's results. Every point whose forced flow passes with a determined head reports it (owner's decision 2026-10-23): a point that has no head after its warm start, while the flow has a way through, is solved again from the initial state and from it with the active control valves open, the first head found, or the finding that a control valve in series is at its switch, being used (with none, its first result is kept), unless its flow exceeds what every way between the pump's sides can pass that way (a cut of FCVs at their setpoints and one-way elements against the flow: no steady state carries it); a point at that limit is also solved with each FCV of the cut held open, to find whether it is at its switch; a point without a head says whether the flow has no way through, no steady state carries it, its head is undetermined (a side on a free level, or a control valve in series at its switch) or its solve did not converge (TSD §5.6), in words (`message`) and as data (`reason`, with the ids and numbers the words quote; for a solve that did not converge, the components `/solve` reports as oscillating, SDD §4.10), which the web app tells with names and display units, the words kept under Details. Every pump's trace defines the system curve (H_sys), and the chart says how the curve shown was computed and links to that trace. *(Usability without trading correctness, GOALS §3.)*
- Boundaries add no entrance or exit loss unless the connection has an entrance or exit fitting; the methods summary and each reservoir and reference-node trace say so, with the web app's default fittings at reservoirs (sharp entrance, exit). Traces, flags and topology issues number a connection's pipes and fittings from 1, as the app does; data indexes (`pipeIndex`, `segmentIndex`, `fittingIndex`) stay 0-based. *(GOALS §4.2.)*
- Model rules JSON Schema cannot express are published from the Pydantic models as OpenAPI extensions (`x-port-ids`, `x-port-roles`, `x-port-count`, `x-required-parameters`, `x-reducer-types`, `x-entrance-types`, `x-exit-types`, `x-setpoint-bounds`, `x-ordered-fields` (also on the goal-seek variable, design-check, group-curve request and pipe-spec schemas), `x-override-fields`, `x-goal-variables`, `x-goal-quantities`, `x-goal-seek-rules`, `x-design-check-presets`, `x-fields-by-value`, `x-reference-fields`, `x-relief-data`); the web app reads them, with the schema's bounds, from the generated `openapi.json` (`utils/model-rules.ts`) instead of copying them, and an API test fails while that copy is stale.
- Topology problems are 422 with every issue listed; validation and fluid-range errors 400; all errors share one envelope.
