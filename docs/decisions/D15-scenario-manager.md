# D15. Scenario manager (owner's request, 2026-10-25)

Decision D15 of the OpenSolve Pipe decision record ([index](README.md)). Decisions override the specs; `docs/GOALS.md` overrides decisions. Code and tests cite this decision as `CLAUDE.md D15`.

Design proposal: [`scenario-manager.md`](../proposals/scenario-manager.md).

---

Built from `docs/proposals/scenario-manager.md` (an API designer, a web designer and a synthesizer, then API and web builders, an independent tester and an integrator). Specs: PRD §3.8, SDD §4.12, TSD §5.7.

### Model

`Project.scenarios` (≤ 20, omitted when empty; `schemaVersion` stays 1, D14): `{id, name, description?, overrides[]}` (≤ 30 overrides). An override names a target, `component {componentId}`, `pipe {connectionId, pipeIndex}` (0-based) or `project`, and a `field` from a **field allow-list** (TSD §12 item 10), not a JSON Pointer, with a JSON `value` in SI checked by the target's own Pydantic field and validators when applied. The list is PRD §3.8's: pump `status`, `speed`, `control.setpoint`; valve `status`, `resistance`, control-valve `setpoint`; reservoir `liquidLevel`, `surfacePressure`; reference-node `pressure`; assigned `flow`; an equipment item's whole `rating` or one of its values, `rating.pressureLoss`, `rating.flow` and `rating.density` (a rated point's) or `rating.value` (a Cv's or Kv's) (D18); an orifice plate's `boreDiameter` and `dischargeCoefficient` (a number, or null for ISO 5167-2's) (D20); a relief valve's `status`, `setPressure`, whole `capacity` or one of its values, `capacity.letter`, `capacity.area` (an effective or a certified area) and a certified capacity's `capacity.dischargeCoefficient` and `capacity.overpressure` (a number, or null for ASME's) (D23); a pipe's `spec` (material, schedule, size and bore/roughness overrides, replaced together, or a project library pipe spec, `{specId}`, D22) and `length`; the whole `fluid` or a built-in fluid's `fluid.temperature`. A valve's `resistance` may be a project library entry, `{kind: 'library', id}` (D22). It is data in `models/scenarios.py`, published as `x-override-fields`. A scenario sets each value at most once, never a value with a part of it (400), so order never matters. Values only, never topology. *(GOALS §4.1: every overridable value is named and typed.)*

### Apply

`/solve` and `/system-curve` take an optional `scenarioId` (body only). `services/scenarios.py` writes the values into the base's JSON (set fields only, `scenarios` dropped) and validates it: the solve equals the hand-edited project's bit for bit, and nothing under `services/solver/` changed. Without `scenarioId` the routers make today's call, so base results are bit-identical with or without scenarios (corpus comparison against `4ccdf9f`: 5,136 identical, no ignores). An override whose target is gone is `orphaned`, one whose target lacks the value (a status on a reservoir, a flow setpoint on a fixed pump, a temperature on a custom fluid, a rated flow on equipment rated by a Cv, a bore on a valve, a rated coefficient on a relief valve sized by a letter) `not_applicable`: kept, reported, ignored, never flagged. Unknown scenario 404; a bad value 400 at its override, never echoed; topology 422 and fluid 400 as for the hand-edited project, naming the scenario by id only (its name is a submitted value). Solve all is one request per case, sequential; no batch endpoint. Scenarios leave `METHOD_VERSION` as it is (1.2.0 then; 1.3.0 since D18, 1.4.0 since D20, 1.5.0 since D22, 1.6.0 since D23): inputs change, calculations do not. *(GOALS §3: correctness and privacy unchanged.)*

### Traceability

Responses carry `scenario` (null for the base): every override with its state, the value used, the base value and unit. A scenario's methods summary opens with a "Scenario" section and each changed element's trace with a note; input sources stay `user`/`default`. The web names the case on every result: header, card, trace ("Changed by this scenario"), copied methods text, chart and comparison. *(GOALS §4.2.)*

### Designers' web defaults (reversible, D14)

A Scenarios button and manager; a case bar (Case select, where edits go, Solve all) once scenarios exist. In a scenario only allow-listed values are editable, marked Changed with the base value and Reset (typing the base value back removes the change); names, project description and display units are shared; everything else is locked by default and topology actions are hidden. Pipe changes follow their pipe objects through base edits (joins, reversals, insertions); a removed pipe takes its changes; a deleted element's changes are kept as no longer applying; a PRV/PSV↔FCV change removes that valve's setpoint changes; new ids never re-use an overridden id. One undo history, each step recording its case. Results, errors, staleness (base fingerprint plus the scenario's overrides: conservative) and system curves are per case; Solve all goes base first, skips current cases, keeps per-case errors and stops on a network error, resumable. Compare cases: differences from the base, relative only for quantities with a true zero, no tolerance snapping, no values for a case that did not converge, failed or was not reached; a case's connection values are read on the connection as it is now (`linkReading`: pipes by identity, the other sign after a reversal, left out with a note where its ends or pipes changed). The chart shows other cases' operating points and pump curves, their system curves on request. The active case is page state: a link opens on the base case. *(GOALS §4.7: every view works on phones.)*

### Proof

The metamorphic reference file (`tests/reference/test_scenarios.py`, by a tester who did not read `services/`), unit tests against a second independent patcher, `tests/differential/scenario_check.py` over the corpus (5,136 projects, 0 different), a shared fixture generated by the real `apply_scenario` for the web's mirror, and the `scenarios` e2e flows on desktop and phone.
