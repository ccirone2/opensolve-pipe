Built from `docs/proposals/goal-seek.md` (model/API, numerics and web designers, a synthesizer, two design reviewers and a reviser; then API and web builders, an independent reference tester, a corpus-tool author and an integrator; its §12 records the as-built departures). Specs: PRD §3.9, SDD §4.13, TSD §5.7.

### Model

`POST /api/v1/goal-seek {project, scenarioId?, variables (1–4), goals (as many)}`; nothing is added to `Project` (`schemaVersion` stays 1). A variable is a numeric value of D15's allow-list addressed as an override (a resistance as one `coefficient`, K, Cv or Kv), with finite SI bounds, `lower < upper`, inside the field's own (`x-goal-variables`, `x-ordered-fields`); statuses, a pipe's `spec`, the whole `fluid` and an equipment item's whole `rating` are not variables (the rating's values are, D18; so are an orifice plate's bore and discharge coefficient, D20, and a relief valve's set pressure, area, rated coefficient and overpressure, D23; its whole `capacity` and its letter are not). The search starts at the case's value, clipped into the bounds (a resistance the case does not hold in that coefficient, an orifice plate's discharge coefficient on ISO 5167-2's default, or a certified relief valve's overpressure on ASME's: the middle of the bounds on the variable's scale); there is no start field. A goal is a port's static pressure, a connection's flow, largest velocity or head loss, a pump's flow, head, NPSHa or NPSH margin, a valve's flow or pressure drop, an equipment item's flow, pressure loss or static pressure drop (D18), an orifice plate's flow, permanent pressure loss, differential pressure at its taps (only a plate with taps, `needs: ['taps']`) or static pressure drop (D20), a relief valve's flow or static pressure drop (D23), or a boundary's outflow (Compare's rows, read from the published fields), with a target and a tolerance: default max(0.5 % of the target, a floor of 0.01 m of head (×ρg of the case fluid for pressures), 10⁻⁶ m³/s or 10⁻³ m/s), the flow and velocity floors this decision's, not D6's; a user tolerance at least max(10⁻⁶ × \|target\|, a fixed minimum per kind that does not depend on the fluid) (`x-goal-quantities`). The request's list rules are `x-goal-seek-rules`. *(GOALS §4.1: every value named and typed.)*

### Search

Every evaluation is `solve_project` of the case with the variables written on top (cold, no system curves); nothing under `services/solver/` changed. Each variable is scaled to [0, 1] (log for lengths, resistances, an equipment item's rated drop, rated flow and Cv or Kv, an orifice plate's bore, and a relief valve's area), mapped back exactly at the bounds and the start and clamped elsewhere, so no trial leaves the bounds; every model rule on these values bounds one value, so validating the 2n bounds before any solve proves every trial validates. An orifice plate's bore and discharge coefficient also meet a topology rule (β < 1 and C ≤ 1, D20), so the network is also built at each bound of such a variable: its `ORIFICE_OUT_OF_RANGE` there is a bounds 400 located by index, with no id or value in the text, and for one such variable alone the two builds prove every trial builds (the rule is monotone in that value); a trial refused where a bore and a coefficient vary together, or a bore on an entered coefficient moved from corner or flange taps, is an unusable trial. A relief valve's four values meet D23's refusal (ASME VIII's 15 psi scope on ASME's overpressure, and a law the floating point can represent), so the network is built at each of their bounds too, in the same way; a scope refusal at a set's bound does not count where the same valve's overpressure is also varied, since every trial then writes one. One variable: the start, a 9-point scan coarse to fine, Brent (xtol 10⁻¹⁰ of the range) in the bracket nearest the start, and a sign change the closest-value search finds is searched too; several: dogbox least squares on residual/tolerance in coordinates shifted to the start, with goal seek's own forward-difference Jacobian (an unusable step retried backward), from the first usable of the middle of the bounds and each variable's scan values when the start itself is unusable. Stop at a tenth of every tolerance; met within it; a start already met stops at once. Unusable trials (not converged, no value, a topology or fluid error at those values) are never residuals: gaps probed (one variable) or penalties (several). Jumps and crossings where only failed solves separate the sides are named and never met; state changes count only elements that carry flow; other crossings, met ranges and values to apply exactly are noted, a plateau is a run of neighbouring tied values, and "not reachable" says only what the values solved show (D13). The reported evaluation is the least by (tier, distance from the start, index), unmet ones by their cost with each residual rounded to 10⁻³ of its tolerance (as built: round-off never picks a value on a plateau); the stop reason follows it. Caps 60 for one variable and 20(n + 1) for n, inside the one 45 s budget (best so far, `time_budget`); at most one goal seek in the worker pool (503 `SERVER_BUSY`), so a solve always has a worker; rate-limited with `/solve`. Deterministic but for a run stopped by time. *(GOALS §3: correctness over convergence.)*

### Results

The reported evaluation's own solved state with a "Goal seek" methods section first (the case, the method, every constant and its citations, each variable and goal with its tolerance's source, why it stopped, the notes) and a note on each varied element; every evaluation listed with its purpose and outcome; each variable's `override`, which applied and solved gives the same state bit for bit; in a scenario run `replacedOverride` and the Scenario section's marks name the overrides the values replaced (a value inside a whole value the scenario sets, a fluid's temperature or a rating's values, gets that whole value holding every value found, D18). Errors in order: request 400; scenario 404/400; case fluid 400; unknown element, port or pipe 404 (ids named); inputs that do not apply 400 (by index, ids only in `componentIds`/`connectionIds`); case topology 422; bounds 400; then always 200 but for a first evaluation out of time (503 `TIMEOUT`). Goal seek leaves `METHOD_VERSION` as it is (1.2.0 then; 1.3.0 since D18, 1.4.0 since D20, 1.5.0 since D22, 1.6.0 since D23) and names it; the search has no version label. No flags are added: a goal not met is not physics. *(GOALS §4.2, §4.3.)*

### Designers' web defaults (reversible, D14)

A Goal seek dialog (two columns from 1024 px, a sheet on phones) from the Results header and from "Use in goal seek" in a trace, on the case shown; default bounds from a web table, always shown and editable; fields never locked in a scenario. One calculation request at a time per page: every Solve control reads one store getter (`calculating`), the store refuses a solve during a goal seek and a goal seek during a solve, and only Cancel stops one. Apply to the case it ran on or as a new scenario (never a scenario run into the base), the exact floats, one undo step, then solved; a result goes out of date by its case's key, recomputed on every change whether or not the project has results. The setup and result are page state; while the setup names an element, no new element takes its id. *(GOALS §4.7: every view works on phones.)*

### Proof

`tests/reference/test_goal_seek.py` (by a tester who did not read `services/`): closed-form inverses for every variable field and goal quantity (G1–G14, G10b, G17, G19–G24), at the default and the smallest tolerance, and the outcome cases (G15 not reachable, G16 an unsolved crossing at a controlled pump's setpoint, G18 met at the start); the metamorphic bit-identity of `override`; unit tests of the pure search on synthetic evaluators; a shared fixture generated by the real trial builder and goal reader for the web's Apply and readers; `tests/differential/goal_seek_check.py` over the whole corpus, 5,136 projects at n = 1–4 (15,282 goal seeks, 0 violations; met 95.1 % of the targets drawn from values the network gives inside the bounds; TSD §10.4); the corpus comparison against `bdbc868` (5,136 identical, no ignores) and `scenario_check` (0 different); the `goal-seek` e2e flows on desktop and phone.
