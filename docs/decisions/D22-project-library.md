# D22. Project library (owner, 2026-10-28)

Decision D22 of the OpenSolve Pipe decision record ([index](README.md)). Decisions override the specs; `docs/GOALS.md` overrides decisions. Code and tests cite this decision as `CLAUDE.md D22`.

Design proposal: [`project-library.md`](../proposals/project-library.md).

---

Built from `docs/proposals/project-library.md` (one designer with a prototype, and the owner's answers of 2026-10-28 in its §10: "Go with your recommendations and build it"; then a contract builder, an API builder, a reference tester who did not read `services/`, a corpus-tool author, web model and UI builders, an example builder, integrators and a gate runner; its §12 records the as-built departures). Specs: PRD §3.1.5, SDD §4.18, TSD §4.11.

### Model

`Project.pipeLibrary` and `Project.resistanceLibrary` (`models/project_library.py`; ≤ 100 entries each, left out of every dump when empty, as `scenarios`, so a project without a library serializes, links and solves exactly as before; `schemaVersion` stays 1, D14). A **pipe spec** `{id, name, source, materialId, innerDiameter, roughness?, outerDiameter?, nominalSize?}`: a library material or `custom`, the bore in (0, 10] m, a roughness in [0, 0.1] m, required for `custom` and absent on a library material for that material's Farshad & Rieke roughness at the spec's bore (as a library pipe with a bore override, proposal §1.2), and an outer diameter (above the bore) and nominal size for display and the web's port sizes only. A **resistance entry** `{id, name, source, kind: 'K' | 'Cv' | 'Kv', value, referenceDiameter?}`: the value as the datasheet prints it, in (0, 10⁷]; a K needs the bore it is stated at, and a Cv or Kv takes none (D18: a K means nothing without its bore). Every entry's `source` is required, 1–300 characters with at least one that is not white space (owner, Q2). **References:** a pipe segment's `specId`, with nothing but its `length` beside it (`materialId` is optional for that case only); a valve's `resistance: {kind: 'library', id}` (`ResistanceRef`; the resistance is a union on `kind`, told apart by a callable discriminator whose error, `invalid_resistance`, never quotes the input); an inline fitting's `resistanceId`, never with `kOverride`, meeting a custom fitting's need for one. They are references, not templates (owner, Q1): an edit to an entry reaches every element that uses it. Ids are unique within each list (400, by index); every reference names its list, so the API resolves a spec and an entry that share an id each in its own, and the web gives new entries ids from one namespace with the elements (`PS1`, `RS1`, …). The rules JSON Schema cannot state are published as `x-fields-by-value` (`PipeSpec`, `ResistanceSpec`: the fields one field's value requires or forbids), `x-reference-fields` (`PipeDefinition`, `Fitting`: the fields a reference stands in for and those required without it) and `PipeSpec`'s `x-ordered-fields`. *(GOALS §4.1: user data, labelled with its source; usability without trading correctness: one value, one place.)*

### Resolution

No new law, and nothing in `gga.py`, `status.py`, `network.py` or `system_curve.py` changed: references resolve inside the network build, where library data is resolved today (`library.resolve_pipe(pipe, specs)`, `valves.valve_resistance(valve, d_ref, entries)`, `fittings.resolve_fitting(…, entries)`; the conversions in `services/solver/project_library.py` and the leaf module `coefficients.py`, where `k_from_coefficient` moved unchanged), so `/solve`, `/system-curve`, scenarios, goal seek, design checks and the corpus tools take them without another call. A spec pipe is solved as the pipe {materialId, innerDiameter, roughness, length} it stands for. A K entry on an element of reference bore D (a valve's inlet end segment, D9; a fitting's pipe `pipeIndex`) takes K = K₀ (D/d₀)⁴, the same head loss K₀(Q/A₀)²/2g at a given flow, written exactly `k0 * (d / d0) ** 4` (`coefficients.k_at_bore`: K₀ bit for bit at D = d₀; `library_check` holds that expression); a Cv or Kv is converted on D by fluids' `Cv_to_K` / `Kv_to_K` (ISA-75.01.01), as one entered there. A fitting's entry is not bounded by `kOverride`'s 10⁴. An element that refers to an entry therefore solves exactly as with the values typed on it, bit for bit (proposal §1.3 decision 4). *(GOALS §4.1: exact, and checkable by hand.)*

### Errors

A reference to an entry the project does not have is a topology issue (422, listed right after `UNKNOWN_PUMP_CURVE`, naming the element and the id): `UNKNOWN_PIPE_SPEC`, `UNKNOWN_RESISTANCE` (a valve's or a fitting's); a spec on an unknown material is `UNKNOWN_PIPE_MATERIAL` at each pipe that uses it, and `ROUGHNESS_OUT_OF_RANGE` and `PIPE_SIZE_OUT_OF_RANGE` on a pipe of a spec name it, as that does ("connection 'L1' pipe 1: pipe spec 'PS1': …", the rest of each message unchanged). An entry the solver cannot represent on an element's bore is `VALVE_RESISTANCE_OUT_OF_RANGE`, in an entry form that also covers a K entry that underflows to 0, or the new `FITTING_RESISTANCE_OUT_OF_RANGE` (K, or n K/(2gA²) for the fitting's quantity n, not finite; or each finite but the connection law's sum Σ n K/(2gA²) over its fittings, for a flow direction, not: one issue on the connection naming its fittings on entries). An entry that breaks its rules is 400 `VALIDATION_ERROR`, never echoing a value; names and sources are submitted text, so error messages name entries by id only. Request-validation locations leave out the resistance union's tag (`main.py`, as `services/scenarios.py` does for a scenario's values): every invalid inline resistance gives its 400 body of `2723d3c` byte for byte (48 of 48 cases); a kind that is unknown, missing or null, or a resistance that is not an object, is `invalid_resistance` at `…resistance` (proposal §12). *(D10.)*

### Traceability

Input sources stay `user` (D10's labels unchanged). A spec pipe's trace gains "Pipe N pipe spec" and takes its nominal size from the spec; its data sources and a note read `project library pipe spec "<name>" (<id>): <source>` (a blank roughness keeps its Farshad source at the bore). A valve or fitting on an entry gains the entry's value as entered (and d₀ for a K), the conversion's equation and correlation, and notes naming the entry with its source and K = K₀ (D/d₀)⁴ with its numbers; its `FittingResult.source` is that provenance where a `kOverride` gives `user`. A "Project library" methods section between "Pipe friction" and "Minor losses", whenever the project has a library: every spec and entry with its values, source and users (each with the K and bore it takes), an unused one "not used by any element", one sentence per conversion used, citing D22 and, with a Cv or Kv, ISA-75.01.01. No flag code is added. One flag case is, in a project with a library: a fitting on a Cv or Kv entry in laminar flow (0 < Re < 2000 in its pipe's reference segment) gets the valve's `CORRELATION_OUT_OF_RANGE` warning, on the connection with `details {fittingIndex, reynoldsNumber}`, since its conversion is the valve's (ISA-75.01.01 without F_R); a K entry, like a `kOverride`, gets none. No flag message changes: the web ends the range flag of a valve's Crane default with "Enter the manufacturer's coefficient as a resistance, or in the project library." (an inline fitting's, "as its K"; proposal §4.3, §12). *(GOALS §4.2.)*

### Scenarios and goal seek

D15's pipe `spec` may be `{specId}` alone (`PIPE_SPEC_KEYS` gains `spec_id`) and a valve's `resistance` a `ResistanceRef`; change texts name entries `project library pipe spec "<name>" (<id>)` and `project library resistance "<name>" (<id>)`. Entries are base data, not scenario targets or goal-seek variables (owner, Q4: the next slice); an override or variable aimed at one, and an equipment rating that refers to one, are 400. A goal seek's resistance on a valve that refers to an entry starts at the entry's value when its kind is the variable's (a K entry's K on the valve's bore, K₀ (D/d₀)⁴), else in the middle of the bounds; each trial and the `override` write an inline coefficient over the reference, and `caseValue` and `baseValue` are the reference object. `prepare` builds the case network first and holds its topology error until after the 404 and 400 checks, so the error order is unchanged.

### Designers' web defaults (reversible, D14)

A **Project library** button before the Fluid chip (an icon, labelled "Library" from 1280 px; below 1024 px hidden while a calculation runs, Cancel taking its place; a repeated click ignored, as Solve's and Cancel's) opens a dialog of two tabs, Pipe specs and Resistances: cards with the name and id, the values in display units, the source and "Used by N"; forms with each error at its field and the published rules under the form; Save one undo step; Delete refused while an element or a scenario's change uses the entry, naming the first, the refusal scrolled into view with the focus left on Delete; a full list (the schema's 100) makes New unavailable and says so in the list, and the pickers offer "New pipe spec…" or "New entry…" disabled, "(a project holds at most 100)"; read-only in a scenario. A form opened from a picker ("New pipe spec…", "New entry…", "Edit in the library") closes the dialog on Save or Cancel, and a new entry made there is used in the same undo step. The pipe segment form has a "Project specs" group in its material select and shows a spec pipe's values read-only with the source; **Use a pipe spec for…** this pipe, every pipe of the same material and size (or on the same spec), or every pipe of the connection, with the count before anything changes, one undo step. The valve forms (`ValveResistanceField`) and the fittings editor's "Fitting N loss coefficient" select (Cited K, K entered here, the entries, New entry…) offer the entries. "Enter a datasheet value" on a valve's Crane-default range flag; trace notes and data sources link to their entries; the ports editor names spec pipes by the spec's NPS. Export: a Project library sheet (each case's entries as solved, with source and users) and entry columns in Pipes, Fittings and Valves, only in a file with a library. The browser converts only a K entry (K₀ (D/d₀)⁴); a Cv's or Kv's K and a Farshad roughness at a spec's bore are the server's (D10: read, never copy). *(GOALS §4.7.)*
- **Condenser water example** (owner, Q6): rebuilt on the library, with NPS 60 headers in one direction and one riser. `PS1`, an NPS 60 carbon steel spec (59.25 in bore, the material's Farshad roughness at it; illustrative, not from a cited table), on 25 pipes; `RS1`, a Cv of 48,800 (Crane's NPS 16–24 butterfly valve K, 25 f_T, extrapolated to the NPS 30 STD bore and converted with fluids' `K_to_Cv`, 48,760, rounded; illustrative), on the six NPS 30 cell valves and the six pump suction lines' butterfly valve fittings. The winter scenario throttles the tower bypass valve to K 16.5 (illustrative) so the return header, riser and tower header stay above atmospheric pressure (wide open, the tower header was 7.4 m of water below it, which no flag reports). Both cases converge with no flag; the link is 5,409 characters.

### Versions

`METHOD_VERSION` 1.5.0 (owner, Q5): the K-at-a-stated-bore conversion is a new calculation, so a result that uses the library names a version that has it (GOALS §4.3, as D18). Its changelog line says that a fitting on a Cv or Kv entry in laminar flow is flagged, as a valve's Cv or Kv is, and that the flows, heads, pressures, statuses, traces, messages and system curves of projects without a project library are unchanged; every link last solved with 1.4.0 shows the method-change notice after its next solve. The cited library does not grow (owner, Q3; D8).

### Proof

`tests/reference/test_project_library.py` (225 tests, by a tester who did not read `services/`): a spec or an entry equal to the values it stands for, bit for bit, on 166 networks in 180 lift runs (1,047 specs and 220 entries; the 166 material lifts alone 789 and 190); NPS 60 by hand (Darcy–Weisbach and Colebrook with Farshad at the bore, 0.0 relative); a K at a stated bore (−2.9×10⁻¹⁵ against K₀(Q/A₀)²/2g); K, Cv and Kv entries against the ISA definition (4.8×10⁻¹¹); entries on two reducers and a two-bore valve in reverse flow against a closed form that does not depend on the bore converted on; a fitting K above 10⁴; edits reaching every user; the errors, never echoed; scenarios and goal seek bit for bit. `tests/unit/test_project_library.py` (58 tests): a looped network on every kind of entry solves as its hand-typed twin, built by an independent resolver, bit for bit, system curves and both endpoints included; a pipe that does not resolve leaves every other pipe its number and a valve or plate its own end pipe; a fitting on a Cv or Kv entry flagged in laminar flow as a valve is; a spec pipe's roughness or bore out of range naming the spec; a fitting entry finite for one unit but not for its quantity, and fittings each finite whose sum is not, a 422 naming them. The corpus comparison against `2723d3c`: 5,168 identical, 0 different, with the two method-version paths. The new `tests/differential/library_check.py`, in place of a fuzz profile, lifts every corpus project into the library (95,501 specs and 47,325 entries): mode `exact` (each K at its element's bore) 0 different, bit for bit, the 384 solves that do not converge included; mode `rebased` (each K stated at 1.1 D) every lifted project bit for bit equal to its inline twin (each K typed as K₀ (D/d₀)⁴), and within 8.53×10⁻¹⁰ of the largest flow and 9.01×10⁻⁵ m of head (1.05×10⁻⁹ relative) of the original, 49 values different only at zero flow, in one project (D13). The three fuzz profiles give the same 9,000 records as `2723d3c` and `missing_result_check` its baseline; on the 5,168-project corpus `scenario_check`, `equipment_check`, `orifice_check` (both modes) and `design_checks_check` 0 different, `goal_seek_check` 0 violations (15,484 goal seeks); the `project-library` e2e flows on desktop and phone. TSD §10.4 has the counts.
