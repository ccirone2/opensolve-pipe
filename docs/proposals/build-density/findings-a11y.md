## 4. Requirements for the redesign
**Keyboard order.** DOM order must equal visual order in both the label-left grid and the stacked layout. Do not use CSS `order` or grid placement that reorders fields. The order is: name → tabs → core fields → each `<details>` summary in sequence → actions. A closed `<details>` takes exactly one tab stop (its `<summary>`), and its contents must not be focusable. If a section auto-opens (set value, scenario change or error), it does so on render, never while focus is inside the form. Opening one must not move focus. Errors on submit move focus to the first invalid field and open its section first. Keep the Prev/Next bars outside the scroll container, and on desktop do not make the new top bar `position: sticky` inside it. If anything must be sticky inside the scroller, add `scroll-padding-top/bottom` equal to its height.

**Collapsed section name.** Keep a native `<summary>` with no `role` and no `aria-label` override. Its visible text is the name: `<summary>Pipe overrides<span class="count">, 2 set</span></summary>`. Write the comma as real text (visually hidden if the design shows "· 2 set") so the screen reader reads "Pipe overrides, 2 set, collapsed". Do not use a middle dot (·) or a badge alone: the dot is read as "dot" or skipped. With nothing set, give no count (not "0 set"). When a scenario change or error opened the section, add the reason to the text, for example ", 1 changed in scenario" or ", 1 error", in addition to the opened state. Do not wrap the summary in a heading. If a heading is needed, put an `<h3>` inside the `<summary>`.

**Help shown only on focus.** This is acceptable only if all of the following hold. (a) Every static hint stays in the DOM, not `display:none`, and is in `aria-describedby`; hide it visually with the sr-only clip pattern while the field is unfocused. (b) The hints that tell the user what to enter (units basis, "gauge", "inlet minus outlet", "difference") stay visible or move into the label. 3.3.2 Labels or Instructions requires the instructions to be available before input; a hint revealed on focus meets this weakly, a hint revealed on hover does not. (c) Revealing a hint must not shift layout under the pointer or the focused field: reserve the space, or place the hint below the field so only content beneath it moves. A reveal that reflows the next field while a user taps it is a 2.5.x/3.2 hazard. (d) A pointer user needs a way to read a hint without focusing the field. Give each field a (?) toggle button, named "Help for Set pressure", with `aria-expanded`. This matters most on touch, where focusing opens the keyboard. (e) Notes that belong to no field (4 on RV1) cannot depend on a field's focus: keep them visible, or attach them to a section's disclosure. Risks: sighted keyboard and low-vision magnifier users miss guidance that is out of view, and the hint appears far from the pointer.

**Height and size.** 36 px on desktop and 40 px on touch is fine for 2.5.8, which needs 24. Select by `@media (pointer: coarse)`, not by width, so a touch laptop gets 40. Keep 4 px or more between adjacent targets. Checkbox and radio rows must make the whole label clickable to at least 24 px. Inputs need a 16 px font on coarse pointers (iOS zoom). Focus ring: at least 2 px and 3:1 against the background (2.4.13 is AAA but cheap), and never clipped by an `overflow` parent. Use `outline-offset` inside or padding on the scroller.

**Label-left grid.** Use real `<label for>` with no `aria-label` that differs from the visible text (2.5.3 Label in Name). Put the unit inside the name, "Elevation (m)", or link it through `aria-describedby`. Radio groups use `<fieldset><legend>` in the left column. The left column's label text must wrap, never truncate (1.4.10/1.4.12). Switch to stacked layout by container query, `@container (max-width: 20rem)`. With text spacing at 1.4.12 values, labels must not overlap inputs.

**Icon-only buttons.** Each needs an accessible name that starts with its visible tooltip or label word (2.5.3). Today they are named correctly ("Remove point 1", "Undo", "Scenarios (1)"). On the mobile header overflow menu: the trigger is "More actions" with `aria-haspopup="menu"` and `aria-expanded`; the menu items are real buttons; Escape returns focus to the trigger.

**Fixed chrome at small heights.** At `(max-height: 30rem)`, let the header, crumb bar and Prev/Next bar scroll with the page (`position: static`), or collapse them, so the form keeps at least 50 % of 320x256.
