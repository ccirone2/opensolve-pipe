# Web UI guide: the patterns new work follows

What the web app's layout is converging on, distilled from the owner's direction and its measured build (`proposals/build-density.md`, `proposals/ui-ux-refinement.md`). Read it before adding a field, a view, a toolbar or a dialog. Every pattern here is a reversible web default (D14); none outranks GOALS: correctness, traceability and longevity are never traded for density.

## The goals

- **Condensed, structured, quick to scan**, and staying so as features add fields: a new field or view gets dense, grouped, consistent UI by being declared, not by a layout redesign.
- **The defining inputs and the answer at a glance**, on a laptop and on a phone, with **nothing the user set, no default and no exception hidden** (D10, D15, GOALS §4.2, §4.6).
- **Phone and desktop equal in capability, each in its own layout** (GOALS §4.7): a table on desktop can be a list on a phone, a menu a sheet; never a feature on one only.
- **Measured, then enforced**: budgets live in tests, so a regression fails CI rather than review.

## Patterns

### Declare, don't lay out
- A Build field is one entry in `utils/field-registry.ts` (facet, tier, label, help, and how a plain field is drawn); its type, bounds, default, choices and scenario status come from `openapi.json` (D10). [`adding-a-field.md`](adding-a-field.md) is the recipe.
- The registry is the one label and unit table: Build, scenario notes, goal seek and the export read it. Guards fail on a schema field with no entry, an allow-listed field with no label, a varied number with no unit, a pressure that does not say gauge or not (D4).
- Facets, in this order on every type: Operation, Rating, Size and position, Fittings, Identification. Core fields are shown; the rest go in one **More**.

### Disclose without hiding
- A disclosure **says what it holds**: More names each field, "(default)" for those at their default; a reference summary carries its key values ("Calculated properties: 62.32 lb/ft³, 1.002 cP", "Per quantity: ft, in, psi, …", "Convergence (advanced): 100 iterations …", "Design checks: opt-in, all off", "Fields (7 of 10)", "The plan: 5 cases by number running: all 5 made").
- **Fields counts what it hides, defaults included.** A results table's column may be hidden by default (`Column.hiddenByDefault`: Results per pump's Hydraulic power, NPSHa and NPSHr, the owner's nit 3 of 2026-11-12; `proposals/pumps-nits.md` item 3); its value stays one step away, in the trace and the export. Fields' count is over the table's own columns, so the table opens as "Fields (7 of 10), Results per pump" ("(8 of 11)" with a Control column), and a remembered column the table lacks is never counted. What the browser remembers is the user's departure from the defaults, under the table's one key: an array of the columns the user hid, the format from before a default existed, read unchanged (no migration, D14); `{"hidden":[…],"shown":[…]}` once a column hidden by default is shown; no key for a choice equal to the defaults. Show all shows every column; Default fields, offered on a table with defaults while the choice differs from them, forgets the choice. A sort asked for from outside the table (the Summary's links) shows the hidden column it sorts by, stored as if its box were checked, and lasts only for the solve it was made on (review PUMPS-NITS-A1).
- It **opens itself** for what the user must see: a set value, a scenario change or base-case note, a pending draft, a warning (an unconnected port, a mismatched size). It never closes itself.
- **A disclosure that holds work to do is drawn closed only when none is left.** Add cases' plan is drawn closed only when every planned case exists, open otherwise; it opens itself when cases come to remain (another preset, a scenario deleted, an Undo), and after the user's own Add it stays as the user left it. Code that opens it sets the element's `open` as well as its bound state, since a user's close reaches the state only with the queued `toggle` event (`proposals/pumps-results-layout.md` §15 item 124).
- **A long data table is its own disclosure**, its summary naming it and counting its rows: "Pump curve at 100 % speed (41 points)", "(1 point)" for one, the count in its own span that never breaks. Open, it is full height, so no box scrolls down inside the scrolling pane; its box scrolls sideways only. Its caption stays the table's name, visually hidden behind the summary's same words. It opens by default where its chart cannot be drawn, and where its reason column has entries (a point without a head, a flow or a rise), so the reasons a note points to ("the data table says why") stay one press away; "Other cases' group curves", whose Note column no note points into, opens only where its chart cannot be drawn. The default only ever opens it: a table it opened stays open while drawn, a browser's `toggle` for a disclosure drawn open is not taken as the user's choice, and the user's opening or closing is kept by the chart while the data table is hidden and shown (`proposals/pumps-results-layout.md` §15 items 191 to 195).
- **A disclosure with a turning chevron that holds another such disclosure, or sits inside one, is a named Tailwind group** (`group/curve` and `group/plan` hold one; `group/detail` and `group/stop` sit inside one), its chevron turned by `group-open/{name}:rotate-90`. An unnamed `group-open:` turns at any open `.group` above it: inside an open curve table every closed Details looked open (§15 items 122 and 197). The Summary view's Fluid card (`SummaryView.svelte`) is an unnamed `group` holding "Sources of the fluid properties", whose summary keeps the browser's own marker, so no chevron there turns with another disclosure.
- **Static help shows on focus** (`help`), floating under its field so nothing moves; **notes about the value always show** (`hint`: live results, a default's basis, a shared curve, warnings, errors, scenario notes). Tell them apart by what the text says, never by its class.
- **A cost stays in sight.** Text that says what a choice costs is a visible hint and the control's description, never help on focus: on touch, the tap that would show it has already paid the cost. The pump chart's select ("each system curve is computed when its pump is shown") and "Also show the other cases' system curves" ("a curve costs about 41 solves of the network") keep theirs visible (`proposals/pumps-results-layout.md` §6.4 item 8). Help on focus fits text fields and selects, and never a cost, never over a control's own output, never where Escape already means something.
- Reference information sits one step away, the way Results shows the fluid: values in the summary, sources inside.
- **Reading help is reference, behind a disclosure named for what it holds.** Text that explains how to read a chart, and holds no value, no warning and nothing the user set, goes into a closed native disclosure (`.more-summary`) whose summary names its contents, in words that follow what it holds: "How to read this chart: the axes, the group system curve, each pump's own system curve" (": the axes, each pump's own system curve" with no group system curve drawn) and "How to read the rings: what a ring is, which curve it lies on" (", when it is called a point of the group system curve" while it holds that rule too). The summary's first words are medium, its clause regular slate-600. Only the user opens it. It comes before the list its text introduces ("The list below says, for each ring, which"). What qualifies the reading stays in sight: a check that disagrees, each ring's own claim, what the axes cut, the cases with no ring, the labels left out. The image keeps every word, and a unit test reads each line of its footer on screen, in sight or only inside one of these disclosures (`proposals/pumps-results-layout.md` §5.3, §6.4 item 17, §15 items 101 and 105).

### Spend vertical space on content
- **One control height**: `--ctl-h` (Build and its menus 36 px with a mouse, 40 px on touch; 44 px where the suite holds touch targets: the header, Results' header buttons). Label beside control in a fixed column, stacking below a 21 rem container (reflow at 320 px); 4 px grid; tabular figures; 16 px input text (no iOS zoom).
- **Chrome earns its row** (≤ 15 % of the Build pane at 1280×800, tested): merge rows (actions beside tabs; Previous and Next in the top bar on wide screens), one-line banners and status lines with a mark (✓, ⚠, ⬣, spinner), icon-only buttons in narrow panes with the word kept for screen readers.
- **A bar that is used now and then becomes a menu** under the button that owns it (the case bar became the Scenarios menu); **don't repeat** what a tab, a chip or a status line already says.
- **One control per action, at the top.** Solve is the header's button (Ctrl/⌘+Enter); Solve all is the Scenarios menu's first button (Ctrl/⌘+Shift+Enter), and the Scenarios badge turns amber with ▶ and the count of cases to solve while there are any. A pane never repeats them: its words name the control with the header's own icon, in one nowrap span with its word (`ControlName`), so they match an icon-only button at 320 px, and the shortcut follows on a fine pointer only (`KeysHint`). A modal over the header keeps its own (the trace's sheet below 1024 px keeps Solve again). On short landscape screens (≤ 20 rem tall, ≥ 35.5 rem wide) the header is one pinned row, above the panes' layers (z 45: the trace's side panel scrolls under it), its height measured for `scroll-padding-top`; narrower short windows scroll as one page (WCAG 1.4.10), the one place Solve is not always in view (`proposals/build-density.md` §19).
- **Groups of tabs or pills are one row that scrolls sideways at every width**, one component, `ScrollRow` (`components/ui/ScrollRow.svelte`: the Results view row and the Pumps tab's section nav). Edge shadows say there is more; a mouse wheel scrolls it sideways while it can move; the selected item and the one after it are kept in view by scrolling the row alone, never the pane, also when the row is drawn again (Compare cases and back). Where the two cannot both fit, the selected one's start wins. Its scrolling element has `py-1`, since `overflow-x: auto` clips a focus ring's top and bottom too; a row whose layout must not move takes `-my-1`, inside a `flow-root` so the gap after it stays. It is `relative`, so the hidden words of an item scrolled out stay inside its clip (`proposals/pumps-results-layout.md` §15 items 66, 73 and 78).
- **A set of pictures is a swipeable row too** (the landing page's How it works, `ScreenshotCarousel.svelte`): scroll-snap for the motion, Previous and Next, a dot per slide, ← and →, the slide shown announced; never rotating by itself. Each picture has a version made for the screen (a `<picture>`, a phone's cropped to what matters), in a frame of its exact aspect ratio that it fills with `object-fit: contain`, so no browser can squash it. Captions go above their pictures; a press always moves the row (snapping off while it does, put exactly in place when the motion ends).
- **Two fields side by side** each sit in their own `@container`, so a field in a narrow half stacks its label above rather than squeezing its box (the label-beside rule reads the nearest container's width).
- **Container queries only where they cannot trap a sheet.** A row or grid in the Results pane follows its container's width, not the viewport's, since the pane is 480 px wide on a desktop: the pump chart's select sits beside its heading from 26 rem (under it, on a phone, it has the row's whole width, so a pump name's end shows), its readout goes two-up from 26 rem and its tables from 40 rem. A container is never a card and never an ancestor of a ResultsTable, a Dialog or a sheet: layout containment would trap a fixed-position sheet (the Fields sheet is `max-sm:fixed`). `tests/pumps-layout.e2e.ts` asserts that no ancestor of a "Fields shown in …" group has a `container-type` other than `normal`. An auto-fill grid (`repeat(auto-fill, minmax(13rem, 1fr))`) needs no container at all.

### Charts and their requests
- **One anatomy per chart**, top to bottom: its heading and its title (the figcaption, which is also the image's title); the canvas; the reading controls (toggle chips, the slider, the readout); one strip for the requests drawn on it; the legend, where it is not inside the canvas (the group chart's); the actions (Show data table, Download image); the notes about the values; the reference, where it has any; the data region; then the other cases under their own heading. A data table opens after the notes, so it never pushes a note away from its chart. The pump chart is built so (`proposals/pumps-results-layout.md` §5.1, §15 items 16 to 46), and the group chart since S3 (§15 items 94 to 105), with its actions before its legend: with the reading controls and the strip above it, the legend first put its Show data table 676 px below the canvas, over its 600 px budget (§15 item 94). Among the notes the checks come first, a ✓ (`aria-hidden`, its own element) before each that agrees and no mark on one that does not.
- **One strip of live lines.** Each request a chart makes has one line: an always-present `<span aria-live="polite" aria-atomic="true">`, the first child of its row, empty when idle. Its button (Cancel, Try again, Compute) comes after it, outside it, and is described by it. It is never `role="status"`, so a pane-wide status query still finds the Results header's alone, and never under an `aria-busy` element: busy is the canvas wrapper's, the part that is redrawn. The Pumps together card has three such lines since S3: the group curve's heads Station, whose shares wait for it; the group system curve's is the group chart's strip; the other cases' sits under their own heading. The card has no `role="status"` (`proposals/pumps-results-layout.md` §15 item 97). A request that left work undone says so in its line too ("Not every other case's station duty was computed: see Running combinations.").
  - A line mounted as its request starts holds back its progress words for two animation frames, so it is drawn empty before it speaks: a polite line inserted already speaking is not announced. A failed or cancelled request is said at once.
  - A polite line that a press may fill with the words it already holds (Add cases' "Now ticked: …", written by every Add that ticks the box) is emptied at the press and written two animation frames later: emptied and filled in one task, the accessibility tree sees no change, so the same words twice are not said. The stop order's moves and Default order write their messages into the same line once the move is drawn, without emptying it first (D24). A line that repeats a visible line for a focus that does not pass it (Add cases' "Now ticked: …", said while the focus stays on Add, before the line; `proposals/build-density.md` §19) goes with the visible line once it stops holding (`proposals/pumps-results-layout.md` §15 item 127).
  - Its mark (the spinner, ⬣) is the span's first element, set at the sentence's first line (`items-start`, the 14 px icon 1 px down), however the sentence wraps.
  - The strip is `sr-only` while it has nothing to say, so it takes no room. Lines about the data ("{n} of {m} system-curve points have no head: …") are plain paragraphs after the request line, with no mark.
- **A reason that lasts is shown; one that passes is not.** Why an action is unavailable for as long as the results stand ("This solve did not converge: its values are not a solution, so no image is made.") is visible 12 px text and the button's description, beside the button or under it, never under another button: the two share one item of the row. A reason that changes on every redraw ("The chart is being drawn.") stays visually hidden and in `title`, so nothing flashes. In a row of two buttons that each may have a reason, the reasons follow the row in the buttons' order, each its own button's description (Add cases' row was one, `proposals/pumps-results-layout.md` §15 items 116 and 128). The Scenarios menu's Solve all shows its lasting reason under it; no row has two such buttons since `proposals/build-density.md` §19.
- **Toggle chips** show a state: `.btn` at the control height with `aria-pressed`, led in both states by one 16 px `aria-hidden` mark in the same place, a checked box (`box-check`, blue-700) on the filled chip when on and an empty box (`box`, slate-500) on the outlined chip when off, so a press changes no chip's width and no row's wrap; their words unchanged. Colour never says "on" alone (`proposals/pumps-nits.md` item 1).
- **Tags are not controls.** "(shown)" is `rounded bg-slate-100 px-1.5 text-xs`, with no border, no pill and no 44 px row; the rounded, bordered 44 px shape is for controls only. A tag beside a heading is the heading's sibling, never inside it, so the heading alone names its region; a panel's tag ("Changes the project") is plain 12 px slate-600 words.
- **A state is a borderless pill.** The API's state word alone (Running, Off, No flow) in a pill tinted by the state, any qualifier after it as plain text: "[Running] (holding flow setpoint)". `inline-block rounded-full px-2 text-xs leading-5 font-medium`, with no border, no icon and no glyph, so it never reads as a flag pill or a control, and no padding above or below, so the row's 20 px line does not grow. The tint is by the state alone, never by the row's flags (`PUMP_STATUS_TONES`: green-200 on green-900 running, slate-200 on slate-700 off, red-200 on red-950 no flow, 7.49, 8.40 and 11.14 to 1); the word carries the state, so colour is never alone, and the cell's words are the label's, word for word (`pumpStatusParts`). Results per pump's Status only; the group table's State and Running combinations keep plain words (`proposals/pumps-nits.md` item 2).
- **No character designates a pump or the group in a table, a sentence or a tag** (the owner's nit 5, 2026-11-12; `proposals/pumps-nits.md` item 5). A pump is its name: "Pumps in the group", the Station table and Running combinations show names alone, with no slot symbol. The duty sentence starts with its words ("Group duty (station's flow): …"), a "(shown)" tag is its words alone ("Base case (shown)"), and a mark the chart draws is named in words, never by a character in parentheses: "Best efficiency point (BEP)", BEP being the cross's label on the chart, and "Shutoff head (the dash at zero flow)". `designators()` (`testing/helpers.ts`) guards these places. The charts' marks, their legends, the "Each pump's point" table in the group chart's data (each pump's slot symbol, or ◇ while it is held, before its name), the case lists and the ring list keep theirs until slices 5b and 5c (the owner's answers of 2026-11-12: cases numbered by their place in the Scenarios list, and the shapes go too); until then the rule below holds for them.
- **A mark named in text is the shape the chart draws.** The pump chart's other cases are △ □ ✳ × ▽, Chart.js's `triangle`, `rect`, `star`, `crossRot` and its triangle turned 180° (the legend's entry turns with it). A character that is also an emoji is written with U+FE0E after it (`'✳\uFE0E'`): without it Chromium draws a coloured picture where the page's font lacks the glyph. A case's mark is fixed by case: its place among the other cases with a result while they are five or fewer, else kept for as long as it stays drawn, never moved by a tick (`caseMarkers`; `proposals/pumps-results-layout.md` §15 items 212 and 213). The group chart's legend still pairs slot 3's ★ with Chart.js's `star` (✳), left for slice 5c (§15 items 212 and 229); since nit 5 the star is stroked in its slot's colour at 3 px, where it was stroked white and could not be seen on white or in the image's legend (`proposals/pumps-nits.md` item 5).
- **A list of marked lines keeps a column for the marks.** The ring list under the group chart is a `<ul>` named by its lead (`aria-labelledby`), so it is told apart from the "Legend" list: one `<li>` per ring in number order, the glyph (`aria-hidden`) and the number in a reserved column (2.25 rem, `whitespace-nowrap`), then the case's name in medium weight and the rest of its entry in a `min-w-0` span that wraps, so every line's words start at one edge. A line's text without its glyph is its entry in the image's sentence, word for word. Where marks come and go the column stays: "Cases on this chart" keeps 2.5 rem for "○ n ·" after each box, so no name moves when a ring is numbered (`proposals/pumps-results-layout.md` §15 items 103 and 105). Where no mark is drawn no column is kept: since nit 5 "Pumps in the group" and the card's two tables have no slot symbol and no 1 rem column for one, so a name starts right after its box or at its row header's edge, at most 8 px in at every size (`NAME_INSET` in `tests/pumps-layout.e2e.ts`; 32 and 28 px with the column; §15 items 87 and 164, `proposals/pumps-nits.md` item 5).
- **A capped choice looks capped and stays readable.** Its box is greyed (`opacity-45`), its row `cursor-not-allowed`, its name kept at slate-600, since the name is what the user reads to choose what to untick. It stays focusable, `aria-disabled`, and described by the visible cap ("At most 6 cases at once."). A choice that would draw nothing takes no place in the list while it draws nothing: no box, and one line under the list names it ("Off in this case (no operating point): Pump PA off; Both pumps off.", a `hint` that wraps any word), before the cap's line. While it draws part of what the others do (its system curve, with the pump chart's other cases' system curves asked for) it has its box and its place again, and says what it does not draw under its name, outside its label, and in its description ("(off in this case: no operating point)"), and can put a case drawn before past the cap (`proposals/pumps-results-layout.md` §15 items 214 to 217).
- **Two lists of the same things share one choice.** "Cases on the chart" and "Cases on this chart" list the same cases for two charts with their own caps and orders: a case the user unticks under either is unticked under both (one set of page state), and ticked again under either it comes back on each chart with room. What a list's cap adds at an untick, the cases past it, unticked so the place left stays free, stays that list's own, since sharing it would untick on the other chart cases the user never touched; and a list that draws nothing at that moment (its card closed, its rings off) holds no place free, unless it holds a choice the user made on it. Such a choice outlives a switch of what the chart is drawn for (another pump) and is forgotten with the project (`proposals/pumps-results-layout.md` §15 items 218 to 220).
- **A press moves nothing under the pointer, also while its answers arrive.** A switch whose press adds or takes away boxes above it ("Also show the other cases' system curves") scrolls its scroller by what it moved once the press is drawn, as a pressed heading's box does. Where the answers it asked for add more above it as they come (each curve's table, with the data table shown), it is held in place on each change of its figure's size, before paint, until the last has answered, the chart goes, or the user takes a step of their own (a press, a key, a wheel, a touch), so a second press lands where the user aims (`proposals/pumps-results-layout.md` §15 item 222). A toggle chip whose press makes the canvas above it a panel taller or shorter (the pump chart's Efficiency, Shaft power and NPSH) scrolls its scroller by what it moved once the press is drawn, from the keyboard too. At the pane's end, where hiding a panel also takes its note below the row and the scroll cannot take it all, what is left is held as room at the figure's foot and scrolled, and the room goes as it is scrolled out of sight. A button whose words swap ("Show data table", "Hide data table") stacks both in one grid cell, the one not said `invisible` and `aria-hidden`, so it keeps one width and moves nothing beside it. Limits: a blank band no taller than the note removed can stay at the figure's foot until scrolled away or another chip is pressed; near the pane's top, on a window taller than about 985 px with a one-pump project, hiding a panel can still lift the row by up to 112 px less the pane's scroll, since the pane cannot scroll above its top; WebKit not run (`proposals/pumps-nits.md` item 1).

### Long views: sections and one way through
- **A card's parts are sections**: each a plain `div` under an h4 (14 px semibold) with a rule above it, the card's own heading an h3 (16 px semibold), a summary inside a section an h5 (`.section-title`). Legends and field labels stay 12 px medium, so no label outranks its heading. The Pumps together card: the members, then Station, Group chart (the other cases at its end under the h5 "Other cases on the group chart", since S3), Add cases and Running combinations (`proposals/pumps-results-layout.md` §5.3, §15 items 48 to 59); Add cases, the part that changes the project, is a framed panel instead (below; §15 items 118 to 130). A section opens with its answer: Station's flow and rise at 14 px, the values semibold, before the table that details them (§15 item 91); Running combinations' lead, which counts what its table holds ("7 cases: 7 with current results (4 physically invalid, none with warnings), none out of date, none without results."), 14 px with tabular figures, its mark an image before the `<p>` named by the worst severity, each count by the rule the table shows, so a case counts as out of date wherever its heading says "(out of date)" (§15 items 137 and 138). Each section is its own component, presentation only; the card keeps what more than one section reads, and the view state that must outlive a section's redraw.
- **The one part of a card that changes the project is a framed panel**, not a section under a rule: `rounded-lg border border-slate-300 bg-slate-50 p-3` in place of the rule, its h4 still 14 px, with its tag beside it ("Changes the project"). Everything in it wraps a long word (`wrap-break-word` on the panel), and the part before a visually hidden last child keeps no margin, so its padding is the same at its foot as at its head. Inside, one structure in every state, so no control moves from one branch of the markup to another and a control in use keeps the focus: the choice first, then what it would do in one disclosure whose summary says how much is done, then one row of its actions, then their reasons, then the way out to a fuller view. Add cases is built so since S4 (`proposals/pumps-results-layout.md` §5.3, §15 items 118 to 130).
- **One table of several cases follows the chart's order, the case shown first.** Running combinations lists the case shown, then the cases in the order the chart lists them, ticked or not, then the cases without values: a choice on the chart never moves a case. A name is a trace button only in the shown case's group, since a trace opens for the case shown; a button elsewhere would pair one case's trace with another case's values. Each line of a case's heading is sticky at the box's visible width (`sticky left-0 w-[100cqw]`, the box a size container), so it wraps in view (`proposals/pumps-results-layout.md` §15 items 147, 148 and 151). It is a `ResultsTable` with row groups (`Table.groups`): the order holds while it is unsorted; a sort by any column makes one flat table with a Case column after the name, which is no sort of its own, and clearing the sort brings the groups back; the trace buttons stay in the shown case's rows in either form (§15 items 167 and 168).
- **A table's title is visible where its section's heading does not name it**: the group table's "The pumps in the group[, {case}]", a 12 px semibold `<p>` above its controls, names its box. Running combinations is named by its h4 and has no second title (§15 items 162 and 173).
- **A closed card says what opening it shows**: a second, muted line under its heading that is the toggle's description while closed (`aria-describedby`), so the toggle's name still starts with the heading's words. The heading's words stay whole on one line; what follows them (the members' names) sits beside them where it fits, else under them.
- **A long view gets one way through: a section nav.** A `nav` named for the view ("Pumps view sections") holds a visible lead word, "Go to", that labels a toolbar (`role="toolbar"`), not a tablist: the arrow keys move between its buttons, and it looks unlike the view row's filled pills (quiet buttons, the current one semibold over a 2 px blue-700 underline, never filled).
  - **Built from what is drawn.** Each section registers its target while it is drawn, through a context the view provides, so the toolbar has one button per section drawn, in document order, and never one whose section is gone. A target is the section's heading (tabindex −1), or the control a card opens with.
  - **One Tab stop.** ←, →, Home and End move between the buttons, wrapping at the ends, their default prevented. The stop is the focused button while the focus is in the toolbar, else the current one, clamped to the buttons drawn (the same section, else the nearest earlier one).
  - **A press** scrolls its target to the top of the pane, smoothly unless reduced motion is asked for, then focuses it with `preventScroll`. Buttons, never links: nothing touches the URL fragment, which is the project (D3).
  - **Where you are.** `aria-current="location"` marks the button whose target was passed last, set by an IntersectionObserver on the pane whose top margin is the line just under the nav, so a target at rest there is seen to arrive and to leave; a press's own scroll is watched to its end before the pane is read again. Only the row scrolls to keep the current button in view.
  - **Marks.** A button carries its section's worst mark, by §5.2's severities: an invalid flag or value, else a warning flag, else a refusal or a failed request; never a design check or a note. Its name comes from `aria-label`, its visible label first: "Running combinations, has warnings". Chromium reads visually hidden words after a label with a space before the comma in every markup tried (a flex item's text, an absolutely placed span, an inline-block one; §15 item 65).
- **Pinned only when it covers nothing being read.** The nav is static at the view's top. It sticks only once the chart under it has scrolled out, so the chart still fits the pane whole, and only while it takes at most 15 % of the pane (the chrome rule above), never under `short:`. Its height is measured, never a constant, so text zoom follows. While it is pinned, the pane's `scroll-padding-top` is its height and 0.5 rem, and each target's `scroll-margin-top` is only what that padding does not hold, since a scroll honours both: a press lands 0.5 rem under the nav, and no focused control or ring is ever under it (WCAG 2.4.11). An arrow key's focus brings a static nav into view; a pinned one is in sight, so its focus scrolls nothing. z 35: above the tables' sticky cells (z 10 to 30), under the header's Scenarios menu (z 40) and the sheets (z 50) (`proposals/pumps-results-layout.md` §5.4, §15 items 60 to 72).
- **The way back.** Each card ends with "Back to the sections", visually hidden until focused, which focuses the nav's current button: from a card's foot the nav is one Tab and a press away. Shown, it lies over the card's foot from a positioned wrapper that takes no room, and takes no pointer press, so showing or hiding it moves nothing under the pointer and takes nothing meant for what lies under it (§15 item 68).

### Phones
- **Tables read as lists** below 640 px: a block per element headed by its name, values as label and value pairs that wrap, "—" out of sight. The table keeps explicit ARIA roles and its headings for screen readers, so CSS never unmakes its semantics.
  - In "Other cases' station duties" (since S5), a cell of words takes a line of its own, its column's words inline before them, in the list's value style (14 px slate-900, as a number's), so the label and the answer read apart; a number stays a pair (`proposals/pumps-results-layout.md` §15 item 153). In ResultsTable, Running combinations, "Operating points by case" and "Other cases' group curves" a cell of words stays a label and value pair, the app's list pattern (§15, S5's review, LAYOUT-2); the extremes, a list by their box, put every cell on a line (below).
  - A line's header is `::before` content from `data-label`. Where the cell's words follow it in the same run of text (a line, not a flex pair), the header ends in a space (`content-[attr(data-label)_'_']`), never a margin, so the cell's accessible name has the space too. In the extremes' list a value with a mark beside it sits on its line by its text (`items-baseline`, the mark `self-center`) (§15 item 145). Running combinations' marked values do the same (§15 item 175).
  - A table in a narrow box reads as a list by its container, not the viewport: the extremes are a table from 26 rem of their box and a list below, their wrapper the container, so the box can drop its frame in the list (§15 items 142 and 145).
  - A group tinted in the table (a stale case, amber) is tinted as one block in the list: the block carries the tint and its lines are transparent, so it never reads as stripes (§15 item 152).
- **A data table's box that scrolls sideways has edge shadows** (`scroll-shadow-x`), as do the shared sideways row (`ScrollRow`: the Results view row and the section nav) and the Pump lineups table: linear gradients, as dark at a full-height box's first rows as at its middle, where the radial ones they replaced faded to nothing at the box's top. Every box of the Pumps tab's two data regions has them, whatever it holds (`proposals/pumps-results-layout.md` §15 items 201 and 202). The Compare cases view's table box (`CompareView.svelte`) has none and is still to change.
- **A grid or flex item that holds a wide table may shrink** (`min-w-0`), unless it is the scroll box itself. A `<details>` keeps its content's min-content width, so one unbroken word in a cell widened the pump chart's one-column grid and the pane scrolled sideways; with `min-w-0` the table scrolls in its own box (§15 item 196).
- **A row's flags are a line under it**, not a last column off screen: one cell across the row, sticky at the box's visible width (`w-[100cqw]` in a size container), named "{pump}, flags:" (visually hidden) for table navigation, each flag's pill (its icon and severity word, `flagTone`) then its sentence, visible and read once, with no `title`. In the list it follows the row's values (ResultsTable's row notes; the Pumps together card's group table since S3, `proposals/pumps-results-layout.md` §15 item 92). A row without flags has no line, and no "None" anywhere. The flags are a list, an `<li>` each, so they never read as one run of notes, and each sentence is its own element: in both of the card's tables, drawn by `FlagLine` through ResultsTable's `flagLine` (§15 items 149, 150 and 163).
- **What a heading did on desktop, a control does on a phone**: "Sort" (field + direction), sharing **one line** with Fields; labels shorten ("Sort", named "Sort by, {table}"; Fields to icon and count below 360 px) rather than wrap. While a sort is on, "Sort" is for screen readers only, and so is Fields' count, which its name keeps (a table with fields hidden by default always has one; review PUMPS-NITS-A2), and in every state the field has no extra end padding for its arrow (Chromium draws the arrow beyond the author's padding), so the field chosen has more room: whole in the condenser's two card tables, but a series station's "Discharge pressure (psig)" is still cut (`proposals/pumps-results-layout.md` §15 item 183). The headings' sort buttons, hidden there, leave the Tab order (§15 item 176).
- **A button whose label holds a name wraps, at every width**: a component's name cannot be shortened, and `.btn`'s `whitespace-nowrap` let one push the Results pane sideways (`proposals/pumps-results-layout.md` F10, §15 item 1). It takes `whitespace-normal`, `text-left`, `py-1.5` and `wrap-anywhere`, since a name may have no spaces, and keeps `.btn`'s `min-h-ctl`, so it is never shorter than the control height (44 px in Results). "Also found: …" on the Pumps together card and "Save and use for …" in the project library take all four. A reservoir's entrance and exit under Fittings take the first three; `wrap-anywhere` is still to add there. In a table's sticky name column the name's button wraps at 12 rem (`w-max max-w-48 wrap-break-word`), since `wrap-anywhere` lowers the column's min-content width and breaks words inside; in the phone's list it takes the line's width and `wrap-anywhere` (the group table, §15 item 92). A legend entry's or a list line's words sit in their own `min-w-0 wrap-break-word` span, so an unbroken name wraps inside its cell, never over the next (§15 item 95).
- **Pickers open as sheets** from the screen's foot at full width over a dimmed page (Fields), as native selects do; Done, a press outside or Escape closes them. Done and Escape give the focus back to the button that opened them, and a control that goes as it is pressed (Show all, Default fields) first moves the focus inside (`proposals/pumps-results-layout.md` §15 item 182).
- **Two-value choices are segments** (one tap); three or more stay selects. Previous and Next stay at the bottom, under the thumb.

### Personal choices stay personal
- Layout and view choices (the pane split, the fields shown per table, as departures from its defaults, the pump chart's panels, whether each chart's data table is shown: `proposals/pumps-results-layout.md` §15 item 204) are remembered **per browser** in `localStorage`, read and written in try/catch: a convenience, never in the link (D3, GOALS §4.5). The one store of project data, the home page's recent projects, was the owner's decision (`proposals/landing-page.md`); any other needs one too.
- Defaults favour the user's likely setting (a new project in US customary units), but **content keeps what it was made with**: the examples stay SI, a link without units shows SI, so links give the same numbers (GOALS §4.3).

### Accessibility is part of compact
- Visually hidden (`sr-only`), not `display: none`, for anything that must stay in the accessibility tree (a list's "—" cell, a phone's heading row, a title the tab already shows).
- A control's visible words are part of its accessible name (WCAG 2.5.3), with one exception: **a switch's state word is its value, not its label; its name comes from its row and column headers** (`aria-labelledby`, the word `aria-hidden`, a test that no name holds it). Targets ≥ 24 px (2.5.8); disclosures are native `<summary>`; axe-core runs in the e2e suite with disclosures open.
- **Two controls with the same visible words get different names** from a visually hidden suffix after the words, so screen-reader lists, rotors and voice control tell them apart while the visible words still start the name (2.5.3): "Show data table of the pump chart", "Details of the point at 317 gpm" (`IssueDetail`'s `subject`). The space before the suffix stays outside its `sr-only` span, so every name computation keeps it. One exception is open for the owner: the group chart's duty-check Details in its notes and in its data table share a name (`proposals/pumps-results-layout.md` §15 item 102). Where the words are a whole button's label in a flex row (a table's Fields), the name is an `aria-label` with the table's caption after a comma, "Fields (9 of 10), Results per pump", since Chromium named a hidden suffix there with a space before its comma; a phone's field is "Sort by, {table}" (§15 item 181).
- **Visually hidden text that is absolutely placed needs a positioned ancestor inside its scroller.** `sr-only` is `position: absolute`: with no positioned ancestor inside the scroller, it escapes the clip and makes the page taller or wider than the window, and then a `scrollIntoView` or a wheel scrolls the whole workspace. The Results pane's scroller, the shared sideways row (`ScrollRow`) and the wrappers of hidden buttons are `relative`; `tests/pumps-layout.e2e.ts` asserts that the page is never taller than the window, never scrolled, and that a wheel over the header scrolls nothing (`proposals/pumps-results-layout.md` §15 item 67).
- **A panel over inert content gives the focus back after the flush that lifts `inert`.** At 1280×800 the trace is a side panel, and the results under it are inert while it is open. Its cleanup gives the focus back to its opener in `tick().then(…)`, and only where the focus fell to the page, so a close that moves the focus on (Show in Build) keeps its own (`proposals/pumps-results-layout.md` §15 item 154).
- **A link inside a sentence stays inline** ("Trace of Pump PA" at the end of the system curve's method sentence): a button drawn as an underlined link, with no 44 px block to split its sentence, under 2.5.8's inline exception.
- **Motion follows `prefers-reduced-motion`.** A spinner is `motion-safe:animate-spin`; a chevron that turns has `motion-reduce:transition-none` (`IssueDetail`, `SummaryView`, `FieldSections`, the Pumps together card's toggle and methods). Every smooth scroll the app starts reads it: `behavior: 'auto'` when it is set, `'smooth'` otherwise (the section nav's press, a row's keep-in-view, the landing page's carousel). The app's other scrolls are instant.
- **A heading for every part** of a long view, visible, so a section has a title on screen and a stop in heading navigation: the Pumps tab's h3 "Results per pump" and "Pump chart", and h4 "Other cases on the pump chart". A new section is a plain `div` with a heading, not a landmark. The regions tests pin (Pumps together, Add cases, the named scroll boxes, each only while it overflows) stay, and the section nav is the tab's one new landmark (`proposals/pumps-results-layout.md` §7). The Pumps together card's sections are h4s: Station, Group chart, Add cases and Running combinations, with "Other cases on the group chart" an h5 under Group chart and the extremes' h5 under Running combinations.
- **A matrix of toggles is a grid: one Tab stop, arrows between cells; a phone shows one row at a time with segments** (the Scenarios manager's Pump lineups, D24). `role="grid"` with explicit roles; the Tab stop is derived from the cell last wanted and clamped to the table, so an undo never leaves the grid without one; Home, End, Ctrl+Home and Ctrl+End; an arrow at an edge is not prevented. The focus goes back to the active cell after a press, an undo or a rename, and its whole ring stays clear of sticky headers. On a phone a picker chooses the row, and its cells are Build's segments with Changed · Base · Reset.
- **A results table's heading row is one Tab stop, and a focus never lands under what its box pins.** From 640 px ←, →, Home and End move between its sort buttons; the stop is the heading last focused, clamped to the columns shown, and an arrow at an end is the box's. A focus by the keyboard or a script is scrolled clear of the sticky name column and heading row, its 4 px ring too, as it comes in (`focusin`, before the browser's own scroll, which leaves a control under a sticky cell where it is); `scroll-padding` put the box under the pinned nav. A press is never scrolled, from its pointerdown to its click, since a touch tap moves the focus after its pointerup. A pressed heading keeps its words where they were, the box scrolling by what the sort added before it, so a second press at one point reverses the order. A press changes the table by whole pixels, since a box's scroll range is whole and the browser rounds a scroll the code sets: where a press changes the table by a fraction of a pixel (a sort's arrow widening it, or a clear narrowing a sort no press made whole), the pressed column, any but the sticky name column, takes the rest of that pixel (a `min-width` on its heading cell, kept until the sorted column, the table's rows or Flagged only change), and the code rounds the box's scroll to a whole pixel itself. So a press at the end of the box's scroll keeps its place too; there, in CI's Chromium, a 0.8 px growth had moved everything in view 0.8 px. A press grows no heading row: a heading's sort button is `align-bottom`, since an inline flex box takes its baseline from its first item, and a sorted numeric heading's arrow, first in its reversed row, grew the heading row 3 px and scrolled the pane with it (`proposals/pumps-results-layout.md` §15 items 177 to 179, and S6, after CI).
- **A scroll box is a Tab stop and a named region only while it is drawn and overflows** (`scrollRegion`, `utils/scroll-focus.ts`; WCAG 2.1.1). Its `tabindex="0"`, `role="region"` and `aria-labelledby` come and go together, measured by a ResizeObserver on the box and its children, a MutationObserver for children added or removed, and the `toggle` of each disclosure it is in, since a browser lays out a closed disclosure's content and opening one fires no resize. An axis that does not scroll (a phone's list, `overflow: visible`) never counts, nor does a pixel's rounding. A box that stops overflowing while it holds the focus keeps `tabindex="-1"`, its role and its name until the focus leaves, so the focus never falls to the page; the page losing the system focus is no leaving. A dialog's body keeps its height-only rule (`focusableWhenScrollable`) with the same focus rule, and a `ResultsTable` given `labelledby` follows this one (`proposals/pumps-results-layout.md` §15 items 198 to 200). The Compare cases view's table box (`CompareView.svelte`) is still a Tab stop and a region whether it overflows or not, and is still to change.

## How a new UI change ships

1. **Measure first** at 1280×800 and 390×844 (and 320 px): what the change adds per row, per screen; whether core fields stay on a phone's first screen.
2. **Declare** fields in the registry; reuse `FieldSections`, `ResultsTable`, the disclosure and sheet patterns above before writing new layout.
3. **Prove** with `tests/build-density.e2e.ts` (its budgets; `tests/pumps-layout.e2e.ts` holds the Pumps tab's), the registry guards, Vitest and the whole e2e suite at both sizes, axe clean. A test that drove an old control drives the new one with the same assertions; never a looser one. A check that a line is on screen reads its classes and, in the browser, its box, never `toBeVisible` alone: jsdom applies no CSS and draws no boxes, and Playwright accepts `sr-only`'s 1 px box. In Vitest, `outOfSight` reads the hiding classes, the `hidden` attribute, inline styles and a closed disclosure. In `tests/pumps-layout.e2e.ts`, `seenLine` reads `seenBox`'s test, no `.sr-only` element at or above the line, and a box at least 12 px tall; `seenBox` alone reads no class. A check on a sentence beside a pill measures the sentence's own element, since the pill keeps its item drawn; a mark's check reads its box and Playwright's accessibility tree, which leaves out what CSS hides; a check of order reads an element's nodes, text included, since `firstElementChild` skips text (`proposals/pumps-results-layout.md` §15, S5's review). A menu that is not a `<details>` (Fields) is opened for axe too (`axeClean`), and a sheet's place is checked in the browser (`fieldsMenuInPlace`; §15 item 186). A rule measured in the browser (a box that overflows) is tested in Vitest with `testing/resize.ts` (`fakeResizeObserver`, `sizeBox`), since jsdom lays nothing out, and again on real boxes resized in the browser. A summary's words are measured in their own span, since its chevron keeps the summary drawn (`readFolds`), and an edge shadow is read from a screenshot (`edgeShadow`; §15 item 207).
4. **Record** the owner's words and every choice with its reason in the feature's proposal (the build-density proposal's §13–§19 are the pattern), and the merge in [`history.md`](history.md).
